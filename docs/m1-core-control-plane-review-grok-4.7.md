# ReadySpec M1 核心控制面设计：Grok 4.7 独立评审

> 评审工具：`pi 1.5.0`  
> 评审模型：`magpie/grok/grok-4.7`  
> 评审日期：2026-11-05  
> 评审对象：`docs/m1-core-control-plane.md`  
> 方式：只读评审，同时核对 `SPEC.md`、`GLOSSARY.md`、`DESIGN.md` 与当前相关实现

## 1. 总体结论

**修改后实施。** 设计与 `GLOSSARY.md`、`DESIGN.md` 的状态语义以及 `CHG-008`（不再恢复 `allowed_os`）一致，也正确接在现有草稿保存、严格校验、摘要锁和 Goss 二进制校验之上。但它还不能直接开工：范围交集合并会改写断言并丢失分项结论，内置编译器的分派信任边界不完整，实现变体与现有自定义 Shell 草稿不兼容。这三处不改，按原文实施会与 `SPEC.md` §3.1 / §5.3 / §11.1 和当前 `internal/plan`、`internal/webui`、`web/src` 冲突。

本设计没有把 SSH、队列或远端执行写成已实现能力。仓库里也还没有编译器、注册表、清单解析和结果归一化。

## 2. 发现

### P0

**P0-1 范围交集合并与 `PropertyOrigin` 不足以还原单项结果**

- 位置：设计 §7.3、§8.1；对照 `SPEC.md` §3.1「不改写方案原始断言」、§5.3 与 `REQ-COMP-05/06`。
- 影响：同一资源属性被收成一个更严的匹配器后，Goss 只给出一个成功位。例如一项要求不低于 8 GiB、另一项不低于 16 GiB，交集是 16 GiB；实测 10 GiB 时弱项应通过、强项应失败。设计中的 `origins` 只有 `role_id`、`item_id`、`template_id`、`template_version`，没有各方原始匹配器，归一化无法重判。
- 修正：第一版只合并完全相同的匹配器。映射必须保存各方原始期望。Goss 结果只提供观测值；各方 `ItemResult` 用原始期望重算。不能证明兼容就返回 `RESOURCE_CONFLICT`，并带上双方 `item_id`。

**P0-2 不可信快照不能按 `compiler` 字符串选择内置实现**

- 位置：设计 §4.2–§4.3；对照 `internal/plan/plan.go` 的 `Load`，以及 `template.v1.json` 中 `implementation` 仍是任意非空对象。
- 影响：今天任何 `PRIVILEGED` 都被拒绝，且没有内置行为可被冒用。按原文后，只有特权模板要求与注册表摘要一致；`source: BUILTIN` 加 `STANDARD`，或 `PLAN_LOCAL` 中写入已知 `compiler` 名，仍可能进入内置编译器。`webui/plans.go` 的 `NormalizeDraft` 会先按内容重写摘要，不能把重写后的摘要当作信任依据。
- 修正：内置实现只从本地注册表条目进入，键为 `template_id + version + semantic.TemplateDigest`。快照中的 `compiler` 只用来核对，不作为分派键。`USER_PUBLIC` 与 `PLAN_LOCAL` 只能走自定义 Shell。`execution_mode: PRIVILEGED` 仍须四项条件全部成立。信任比较必须在摘要重写之前，并复用 `internal/semantic`，不能另写摘要。

**P0-3 收紧 `implementation` 会破坏现有草稿与测试**

- 位置：设计 §4.2、§11；现有契约在 `web/src/Workbench.tsx` 的 `addShell`、`internal/webui/server_test.go` 和 `internal/plan/plan_test.go`。
- 影响：工作台保存的是 `{kind: CUSTOM_SHELL, command, expect_exit_code}`。`draft.v1.json` 与 `plan.v1.json` 都要求 `implementation` 为对象。若改成只接受 `{kind: BUILTIN, compiler, compiler_version}`，`LoadDraft` 会拒绝尚未完成的草稿，与设计 §11 相反。旧 Python schema 的 `NATIVE/SHELL/FLAT` 不是 Go 契约，不能拿来兼容。
- 修正：用判别联合保留 `CUSTOM_SHELL`。严格校验只拒绝无法编译的变体，保存草稿不升级、不重签。内置模板使用独立变体；自定义脚本继续与参数分离。

### P1

**P1-1 领域类型的失败阶段与现有校验器脱节**

- 位置：设计 §5.1、§5.4；`internal/plan/parameters.go`。
- 影响：`SPEC.md` §5.3 要求静态校验就拦截非法类型。设计把规范化放在编译输入，容易让非法容量拖到编译才失败。`parameterSchema` 只保留编译后的 schema、属性名和 default；`jsonschema/v6` 不会自动保留未注册的 `x-readyspec-type`。
- 修正：领域语法在 `plan.Load` 失败；字节数、时长等只作为编译值，不回写方案。类型元数据从原始 `params_schema` 读取。缺比较策略时明确拒绝，禁止套用 SemVer。

**P1-2 覆盖相等性、诊断响应和参数职责会分叉**

- 位置：设计 §5.2–§5.3、§9；`plans.go` 的 `writeError`；`web/src/api.ts`。
- 影响：`8 GiB` 与 `8GiB` 在规范化前会误报 `OVERRIDE_CONFLICT`。前端只认 `{error: string}`，只返回 `diagnostics` 会变成「请求失败」。`plan.Load` 已经合并默认值并校验三态，再做一套解析器会产生两套结果。
- 修正：冲突比较使用规范化值，报告仍引用原始表达。响应同时保留 `error` 与不含参数原值的 `diagnostics`。`Load` 只做结构、引用、摘要和信任；有效值与来源只由一个解析器产生。

**P1-3 路径、命令键和测试观测值尚未约束**

- 位置：设计 §5.4、§7.4–§7.5、§12.2。
- 影响：路径是否绝对、是否 `Clean`、是否拒绝 `..` 会改变检查对象。命令文本作资源键会泄漏参数并导致 YAML 不确定。H02/H03 若直接读本机 `/proc`，PASS/FAIL 会随开发机变化。
- 修正：路径规则写成校验器行为。命令资源使用稳定别名，脚本与参数分离。集成测试只用临时目录和固定输出的受控命令。

**P1-4 `Verdict` 与拓扑容易提前采集或算错**

- 位置：设计 §6、§8.2–§8.3；`SPEC.md` §6.2、§11.1。
- 影响：实机身份需要 `machine_id`、`boot_id` 和主机密钥指纹，本阶段没有采集器。单项结果是单值；「失败同时有取证错误」若生成两条结果，会和门禁计数冲突。取消、试跑、局部、仿真和空必检集都会改变 `Verdict`。
- 修正：拓扑和结论都做成纯函数，输入由夹具提供，禁止在这些包中访问 SSH 或 Goss。一个检查项只有一个 `ItemResult`，并存错误放进证据。`Verdict` 的输入至少包含方案状态、任务类别、范围、执行器和任务状态，并按 §11.1 的三条规则逐项测试。

**P1-5 API 与批次顺序需要贴住现有入口**

- 位置：设计 §9、§13；`server.go` 已有 `POST /api/v1/plans/validate`。`SPEC.md` §10.2 的 `/plans/{id}/validate` 尚未实现。
- 影响：再做一个按 ID 校验会与当前「请求体携带文档」重复。批次 B 要求映射测试，批次 C 才做归一化，顺序无法验收。清单放在 E，但覆盖语义在 A，接口边界不清楚。
- 修正：M1 继续无状态文档接口，把带 ID 的方案库留到已有发布存储之后。首批按「一个模板、编译、映射、归一化」垂直交付。解析器只接收已经结构化的组和主机覆盖，不读取清单文件。

**P1-6 模板契约不能边写边发明**

- 位置：设计 §1、§7、§14；规范性内容在 `SPEC.md` §6.1，但没有 Goss 资源名、属性、JSON 路径和 `UNSUPPORTED` 条件。
- 影响：36 项会在实现时临时决定观测方式，随后难以与规格复核。
- 修正：每项先固定一页映射再编码。Goss v0.4.9 不能可靠表达时保持「规格定义」，不得用第二次执行补结果。

### P2

- 设计 §5.1 未提 `secret_ref`。本阶段不支持就应显式拒绝，不能当成普通字符串。
- `GET /templates/{id}/{version}` 要求版本不含 `/`；现有版本没有该约束。
- 设计 §13 要求每批重建三个发布二进制。A–C 没有用户可见变化时，只需单目标测试二进制。
- 编译器版本变化会改变 `semantic.TemplateDigest`。行为变化必须同时提升模板版本，不能只改 `compiler_version`。
- 禁用项应不进入 Goss 配置，并由归一化直接给出 `SKIP`。设计 §8.2 只给了状态，没有给编译规则。

## 3. 专项判断

| 主题 | 判断 |
|---|---|
| 可信模板 | 方向正确，并与 `plan.Load` 当前「特权一律拒绝」的注释衔接。必须在摘要重写前比对注册表，且内置编译器只能由注册表条目启动。摘要算法只使用 `internal/semantic`。 |
| 参数三态与覆盖 | 与 `SPEC.md` §5.2 和现有 `explicit_null_params` 一致。缺的是单一解析器、规范化后的冲突比较，以及领域类型进入严格校验。 |
| Goss 合并 / `PropertyOrigin` | 相同期望合并、执行方式隔离、冲突定位是对的。范围交集合并在当前映射结构下不可接受。 |
| 结果归一化 | 五态与「缺失不是通过」符合规格。多属性细节可以保留，但顶层仍是一个 `ItemResult`。`Verdict` 不能从静态编译成功推出。 |
| 兼容性 | `allowed_os` 继续拒绝是对的。自定义 Shell 形状必须继续保存。导入保持 `normalize_draft: false`；工作台校验目前会发送 `normalize_draft: true`，只能规范化作者自己的草稿，不能借此信任内置模板。 |

## 4. 最小首批交付与验收

只做一条垂直切片，不把 36 项或 Ansible 清单放进首批。

1. 注册表接入 `plan.Load`：伪造内置身份、重签摘要、特权升级均拒绝；合法注册表条目才放行。
2. 参数解析器替换 `parameters.go` 中的默认值合并，覆盖三态、来源、同值组和 `OVERRIDE_CONFLICT`。
3. 仅实现 **S01 路径存在与类型**。它有原生文件资源，可在临时目录完成六类测试，不读开发机 CPU 或内存。
4. 只合并完全相同的匹配器；`exists` 与 `filetype` 保持多个属性来源，冲突能定位到两个检查项。
5. 模板 API 区分「规格定义」和「可加入」。前端删除对执行语义的第二份目录，只保留展示；`web/src/catalog.ts` 不再决定能否使用。
6. 旧自定义 Shell 草稿仍可保存。严格校验或编译对尚无实现的模板给出稳定错误，不改写其 `implementation`。

首批通过标准：

- 相同输入得到字节级相同的配置和映射摘要。
- S01 的通过、失败、边界、权限错误、现场覆盖和属性映射都能从 Goss JSON 回到正确的角色与检查项。
- 校验和编译响应不会被界面显示成环境就绪；现有「静态校验通过。此结果仅验证方案文件，不代表目标环境已经就绪。」语义保持不变。
- 保存旧草稿、伪造特权模板、显式空值与未知参数的现有测试继续有效。

H02、H03、S04 放在受控命令夹具之后。全量 36 项、清单和拓扑纯函数仍属于 M1 最终验收，但不是首批门槛。

## 5. 设计中的优点

- 模块依赖方向正确：领域包不依赖 HTTP，编译器不读清单、不发起 SSH。
- 特权信任与自洽摘要被明确拆开，直接对应 `plan.go` 里已经写下的限制。
- 模板可用性以后端注册结果为准，与 `Templates.tsx` 已有的「规格定义」和 `DESIGN.md` 的状态映射一致。
- 自定义 Shell 的参数注入要求可测试，且与 `REQ-SEC-08` 一致。
- 现场值位于执行配置而不是方案中，避免把 `FieldOverride` 写回 `Plan`。

## 残余风险

Goss v0.4.9 对命令输出、超时和非零退出的 JSON 形状，仍要以仓库内嵌二进制的实测为准；设计 §7.5 的门槛是对的，但实测前不能把资源属性写成已证实契约。`Verdict` 的完整优先级即使做成纯函数，也不能在没有真实 `native_ssh` 全量门禁时产生 `READY`。
